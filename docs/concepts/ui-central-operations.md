# Metis UI–central 通信規格：操作

更新日：2026-09-30

本書は設計議論での合意事項をまとめたもの。具体的なAPIパス、フィールド名、通信実装は未確定であり、既存コードの仕様ではない。

## 1. 操作要求と受付応答

- UIからの操作要求はPOST、状態参照はGET／QUERYとする。
- centralはagentへ要求を転送し、agentが要求を永続記録した時点を「受付完了」とする。受付と実行完了を区別する。
- POSTはagentの受付確認まで待機し、受付完了なら202を返す。
- 期限内に受付を確認できなければ504を返し、「受付未確認」として記録を保持する。これは操作失敗を意味しない。
- 受付未確認時の自動再送は行わない。
- 待機期限は機器別に設定し、ユーザー設定値には管理者上限を設ける。
- 拒否理由は共通形式とする。受付前の拒否と、受付後の異常終了を区別する。

## 2. 受付後の状況把握

- 操作要求に対する能動的な応答は受付完了で終了し、成功・完了の個別通知は行わない。
- 以後、ユーザーは監視を通じて設定値、観測値、機器状態を確認する。これを運用ルールとする。
- 設定値と観測値の差が許容範囲内なら正常とする。
- 許容範囲外でも状態変化中なら異常とはせず、状態変化中でなければ異常とする。
- 要求値への到達や操作成功を通信規格として保証しない。
- UIが制御中の更新を受信できなくても、設定値と観測値が許容範囲内で一致していれば問題ない。制御状態への遷移を必ず受信する必要はない。
- 受付後の異常終了は、個別の操作結果通知ではなく、警告として全UIへ配送する。

## 3. 更新と同時操作

- agentは差分更新を許さず、絶対値を指定した更新を扱う。これにより重複要求による値の累積を防ぐ。処理そのものの重複実行を一律に排除する方式ではない。
- 複数ユーザーからの同時操作を許可する。
- 要求はagentへの到達順に処理し、新しい要求を有効として設定目標値を変更する。UIの送信時刻は順序判定に使わない。
- 制御中でも目標値の変更を可能とする。誤入力を直ちに訂正できることを重視する。
- 制御中の変更を許可できない場合は、agentの制御条件に従ってブロックする。

## 4. 実行条件と異常終了

- 測定開始やリセットなど、繰り返しに影響がある操作は、agentが実行前提条件を確認し、必要に応じて実行をブロックする。
- 二つ目の要求も受付完了にはなるが、実行条件を満たさなければ異常終了とする。
- 前提条件の確認から実行開始までをagentでガードし、その間に別要求が割り込まないようにする。
- このガードは実行開始までの判断を保護するものであり、制御が完了するまで後続要求を一律に止めるものではない。開始後の目標値変更はagentの制御条件で判断する。
- 受付完了後に実行条件を満たさず異常終了した場合は、警告としてcentralを通じて全UIへ配送する。操作要求元への個別結果通知は追加しない。
- 警告は既存の警告・acknowledge規格に従う。誰か一人のacknowledgeで警告全体を確認済みとし、警告とacknowledgeの履歴を閲覧可能にする。

## 5. 識別と記録

- centralと一つのagentの一制御を `trace-id` で識別する。
- 個別メッセージを `message-id` で識別する。
- 複数agentにまたがる処理には `workflow-id` を用いる。
- central–agentメッセージでは、機器ID、操作名、ユーザーID、ブラウザー画面のUI識別子、送信時刻、識別子などを共通ヘッダー情報とし、機器固有の操作内容はペイロードに置く。
- 操作名・スキーマはagent登録情報として更新時刻・旧版履歴とともに保持する。
- 制御記録にはスキーマ版や登録履歴への参照を残さず、必要になったら追加する。
- 受付未確認、受付完了、処理中、成功、失敗、結果不明などの先行するcentral–agent側の状態管理と、UIへの能動的な結果通知の有無は区別する。

## 6. central–agent 規格への反映事項

1. 差分更新を許さず、絶対値更新を扱う。
2. 要求をagentへの到達順で処理し、許可される場合は新しい設定目標値を有効にする。
3. 繰り返し操作と制御中の変更について、agentが実行条件を判断する。
4. 前提条件の確認から実行開始までをガードする。
5. 受付後の異常終了を警告としてcentralへ伝え、全UIへの配送につなげる。

本書は反映すべき内容を整理するものであり、別のcentral–agent規格ファイルを更新したものではない。

# Metis テレメトリーのヘッダー：設計メモ

2026-09-28。会話で合意した通信上の最小構成を記録する。実装済みの API 仕様ではない。警報の保存・確認については [alarm-delivery.md](alarm-delivery.md) を参照する。

## 基本方針

テレメトリーは大量に発生し得る観測情報であり、個々の通知の欠落は許容する。警報や操作と同じメッセージ構造（ヘッダーとペイロード）を用いるが、追跡用 ID を全通知に要求しない。メッセージの共通部分とタイプ固有の項目を分けて扱う。

| ヘッダー項目 | テレメトリーでの扱い | 意味 |
|---|---|---|
| タイプ | 必須 | メッセージがテレメトリーであることを示す。具体的なフィールド名と値は未決定。 |
| 送信時刻 | 必須 | agent がこのメッセージの送信を開始する直前の時刻。測定時刻や central の受信時刻とは異なる。具体的なフィールド名と時刻形式は未決定。 |
| `message-id` | 任意 | 個々の通知の追跡が必要な場合に利用できる。通常のテレメトリーでは生成を要求しない。 |
| `trace-id` | 必須ではない | テレメトリーの通常配送には要求しない。 |
| agent ID | メッセージには必須としない | central は WebSocket の認証済み接続、または HTTP の認証済みリクエストから発信 agent を確定する。 |

central は通信から確定した agent ID を受信・保存するテレメトリーの記録に関連付ける。メッセージに agent ID を追加する実装では、認証から確定した ID と一致するかを検証する。HTTP の接続再利用は認証済みリクエストの代わりにはならない。

## ペイロードと鮮度

測定値と、その**測定時刻**はテレメトリーの内容として扱い、ヘッダーの送信時刻と区別する。送信待ちやネットワーク遅延があっても、測定時刻を送信時刻で上書きしない。central は遅れた値を現在値として表示しないため、測定対象と時刻を解釈できる必要がある。

同じ agent が複数の機器やチャンネルを扱うため、agent ID だけでは測定対象を特定できない。対象 ID をペイロードに置く案があるが、その具体的な位置と階層（機器、チャンネル、観測項目）は未決定。

## 利点と制約

- 必須ヘッダーを小さくし、高頻度の通知で ID の生成・記録を強制しない。
- agent ID を通信認証から確定するため、メッセージ内の自己申告だけを信頼しない。
- `message-id` を省略した通知は一件ごとの配送・重複判定ができない。欠落を許容する方針と整合するが、鮮度・順序の対策は別に必要である。

## 今後決めること

1. ヘッダーの具体的なキー名、タイプ値、時刻形式、送信開始時刻の記録方法。
2. ペイロードにおける対象 ID、測定時刻、測定値、単位、品質の構造と必須性。
3. 同じ対象から続けて届く値の順序と鮮度の判断方法。通し番号を必要な対象に採用するかどうか。
4. 接続断後の現在値の再取得、欠落の扱い、保存期間。これらは個別通知に ID を必須とする理由にはならない。

## 議論の経過

- 当初は「送信時刻、`message-id`、タイプ」をヘッダー候補とした。
- 大量で欠落を許容するテレメトリーでは `message-id` を任意とし、タイプと送信時刻を必須とした。
- agent ID は WebSocket の認証済み接続または HTTP の認証済みリクエストから確定し、メッセージには必須としない方針とした。警報でも同じ認証上の識別が必要である。

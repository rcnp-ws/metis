# Metis 制御・応答の通信規格：設計メモ（第２版）

2026-09-29。議論で決定した通信の意味を記録する。実装済みの仕様ではない。具体的な JSON キー、API パス、装置ごとの成功条件は別途定める。警報とテレメトリーはそれぞれ [alarm-delivery.md](alarm-delivery.md)、[telemetry-header.md](telemetry-header.md) を参照する。

## 通信の境界と識別子

UI は central の API を呼ぶ。制御要求は POST、状態参照は GET または QUERY を使う。UI が `trace-id` を発行・保持する必要はなく、個別の制御結果を ID で照会する API も必須とはしない。複数 UI には、対象の現在状態と制御が進行中かどうかを central が提供する。

central は一件の agent に対する制御に一つの `trace-id` を割り当て、central→agent→central の受付、処理、結果で維持する。個々のメッセージには別の `message-id` を付け、各段階を記録する。複数 agent の操作をまとめる場合は、全体に別の `workflow-id` を割り当て、その下に agent ごとの `trace-id` を関連付ける。全体の成否や途中失敗時の処理は未決定。

central は認証済みの UI リクエストからユーザー ID を確定する。UI が申告するユーザー ID はそのまま信用しない。UI 識別子は個々のブラウザー画面ごとに発行し、その際のネットワークアドレス、ブラウザーの種類、ユーザー ID とセットで DB に記録する。閉鎖時には失効の記録を試み、届かなかった場合にも keep-alive の停止と期限切れで失効を判断する。ネットワークアドレスはプロキシ経由では端末のアドレスとは限らない。

## メッセージのヘッダーとペイロード

ヘッダーは配送、追跡、対象、発信元に関する共通情報を扱い、ペイロードは装置固有の制御要求または応答内容を扱う。ここでいうヘッダーは Metis メッセージ内の論理区分であり、HTTP ヘッダーそのものとは限らない。

| 項目 | central→agent の制御要求 | agent→central の応答 |
|---|---|---|
| `trace-id` | この agent との一件の制御の値をヘッダーに含む | 同じ値をヘッダーに含む |
| `message-id` | この要求メッセージ固有の値をヘッダーに含む | 各応答メッセージ固有の値をヘッダーに含む |
| 送信時刻 | ヘッダーに含む | ヘッダーに含む |
| 制御対象機器 ID | 対象およびペイロードのスキーマ選択のためヘッダーに含む | 対応する対象を識別できるようにする。応答での配置は未決定 |
| ユーザー ID | central が認証結果から設定し、ヘッダーに含む | 省略し、central の制御記録から参照する |
| UI 識別子 | ブラウザー画面の値をヘッダーに含む | 省略し、central の制御記録から参照する |
| 操作名 | agent が実行する操作を指定する。ヘッダー／ペイロード上の位置は未決定 | 元の制御記録から参照できる。応答に載せるかは未決定 |
| 制御・応答の内容 | 選択した操作のスキーマに従う装置固有の要求をペイロードに含む | 受付、処理中、結果などをペイロードに含む |

操作と警報には `message-id` を使用するが、テレメトリーでは任意とする。「共通ヘッダー項目」は全タイプでの必須を意味しない。発信 agent の ID は認証済み接続または認証済みリクエストから確定し、central の記録に関連付ける。`workflow-id` を個々のメッセージに載せるか、central の親子関係の記録だけに置くかは未決定。

## 操作スキーマの登録と履歴

agent は登録時に、提供する操作名と各操作のペイロードスキーマを central に伝える。central は登録時刻と旧版を含む履歴を DB に保持する。個々の装置のペイロードを全装置共通の形にする必要はない。機器 ID と操作名だけではスキーマ更新時の版を特定できない点に留意する。

各制御記録には、適用したスキーマ版への明示的な参照を**残さない**。過去の制御は、記録時刻とスキーマ履歴を突き合わせて解釈する。更新の境界付近などでは実際に適用した版を確定できない場合があることを許容し、必要になったとき版参照の追加を検討する。

## agent の受付と POST の HTTP 応答

agent は受付時点で形式、対象、操作、およびその時点で確認できる条件を検証する。適合すると判定した要求を永続記録した時点で「受付完了」とする。受付後に機器の条件が変わる可能性があるため、実行時に必要な条件は再確認する。UI 側のスキーマ検証は便宜上行えても、agent の受付時検証の代わりにならない。

central は agent の受付完了を確認してから、UI の POST に `202 Accepted` を返す。これは agent が依頼を保持したことを示し、機器の状態変更成功を示さない。POST で agent の受付を待つ期限はユーザーが機器ごとに設定できるが、管理者の定める上限を超えない。この待機期限と、装置の成功判定期限は別である。

受付応答が届かない場合、central は「受付未確認」を保持する。まず agent からの応答を待ち、速やかに届かなければ、同じ `trace-id` の受付記録を agent の API で照会する。受付済みを確認できれば `202` を返す。期限までに受付の有無を確認できなければ、`504 Gateway Timeout` と「受付の成否は未確認」と示す本文を UI に返す。`504` は agent が受け付けなかった証明ではなく、UI や central が新しい制御として自動再送する根拠にはしない。具体的な待機・照会タイミングは未決定。

agent が要求を受け付けないと判定した場合は「受付失敗」を UI に返し、共通形式の拒否理由を示す。拒否理由の種類、具体的な本文、HTTP ステータスは未決定。「受付未確認」は、機器への命令が届いた可能性があり制御結果を判定できない「結果不明」とは別である。

## agent の処理状態と結果

| 状態 | 意味 |
|---|---|
| 受付完了 | 受付時点の検証と制御内容の永続記録を確定した。機器の変更成功ではない |
| 処理中 | 受付後、完了前。キュー内の待機も含め、「待機中」という別状態は設けない |
| 成功 | 機器ごとの期限内に、要求された状態への変更を装置ごとの方法で確認した |
| 失敗 | 明確な拒否・エラーを受けた、または期限内に成功条件を満たさないことを観測した。理由も記録する |
| 結果不明 | 命令が機器に届いた可能性を排除できず、通信断などで成功・失敗を確認できない |

例えば、agent が機器へ命令を送った直後に通信が切れ、読み戻しもできなければ結果不明となる。機器に送る前の通信不能で命令が届いていないと確定できる場合とは区別する。期限内未達を観測できた場合は失敗理由として記録し、観測不能なら結果不明とする。成功判定方法、許容差、安定時間、期限は機器ごとに定め、ユーザーが参照できるようにする。後から判明した装置状態も事実として記録する。

## 実装時に残る事項

- メッセージの具体的なキー・型・時刻形式、操作名と `workflow-id` の配置、応答と受付拒否理由の共通形式。
- POST の機器別待機設定と管理者上限、受付記録照会 API、`504` の応答本文、受付拒否時の HTTP ステータス。
- UI 識別子の発行形式、閉鎖・keep-alive の方法と期限、発信元記録の保持期間。
- 二重実行を許さない操作の再試行規則、制御中と判定する範囲、装置ごとの成功判定条件。
- `workflow-id` で束ねた全体の状態、個々の `trace-id` との関係、途中失敗時の取り扱い。

## 更新履歴（議論の要点）

- 初版：UI→central の POST／GET／QUERY と、central→agent→central の一件の制御につき一つの `trace-id`、個々の通信の `message-id` を整理した。agent の検証後の永続記録、処理中、成功・失敗・結果不明を区別し、agent の受付完了後に `202` を返すと決めた。
- 第２版：機器 ID と操作名、時刻付き操作スキーマ履歴を追加。スキーマ版への制御記録からの参照は設けないと決めた。機器別・管理者上限付き待機期限、受付未確認時の `504`、共通形式の受付拒否理由、ブラウザー画面ごとの UI 識別子と keep-alive、複数 agent の `workflow-id` を反映した。

# Metis UI–central 通信規格：監視

更新日：2026-09-29

本書は設計議論での合意事項をまとめたもの。具体的なAPI、フィールド名、通信方式、保存実装は未確定であり、既存コードの仕様ではない。

## 1. 配信対象とフィルタリング

- central は全監視値を接続中の各UIへ配信し、表示対象のフィルタリングはUI内で行う。
- UIからcentralへ購読条件を登録・変更・解除する方式は採用しない。
- 表示対象の切り替えはUI内で完結する。
- 通信量とUIの受信処理量は全監視値の量に依存する。

pub-sub の考え方で配信するが、特定のブローカー、プロトコル、WebSocket等の通信方式を決定したものではない。

## 2. 接続時の最新値配信

- UIが初めて接続した際、central が保持する最新値を配信する。
- central が稼働を継続している間にUIとの通信が一時的に途切れた場合、再接続時にはcentralが保持する最新値を配信する。
- 切断中の全更新を履歴として再配信する方式は採用せず、現在の状態を復元する。

## 3. central の起動識別子

- central は起動ごとに新しい起動識別子を生成し、UI接続時に通知する。
- UIは前回の識別子を保持し、再接続時に比較する。

| 比較結果 | 扱い |
|---|---|
| 前回と同じ | 同じcentralが稼働を継続しており、接続が一時的に途切れたケース |
| 前回と異なる | centralが再起動したケース |
| 前回の識別子がない | UIからは初回接続として扱う |

通信が途切れた時点で、UIだけからネットワーク断とcentral停止を確実に区別することはできない。識別子による判別は再接続後に行う。同じ識別子でも、接続断の具体的な原因までは特定しない。

起動識別子の名称・形式は未確定。

## 4. central 再起動後の復元

- central 再起動後は、全agentへ最新情報の取得を要求する。
- この取得はcentralの起動処理として行い、UIからの要求を待たない。
- 全agentの応答を待って一括提供するのではなく、取得できた情報からUIへ提供する。
- 未取得の対象を明示する。
- 再起動前の保存値があっても、再取得できるまでは最新情報として扱わない。

全agentへの取得要求と取得済み・未取得の管理はcentral–agent通信規格への追記事項。UI–central側では、その結果と状態をUIへ伝える。

## 5. 接続後の更新配信

- 監視値は、値が変化したときに配信する。
- 初回接続・再接続時の最新値配信は、値の変化の有無にかかわらず行う。
- 監視値の途中の欠落を許容する先行方針を引き継ぐ。定期テレメトリーでは `trace-id` と `message-id` を必須としない。
- 取得が停止した場合は、その状態をUIへ伝える。

## 6. keep-alive と取得状態

- agent のkeep-alive情報に取得状態を含める。
- agent からcentralへ伝え、centralからさらにUIへ伝える。
- これにより、値が不変でも取得が継続している状態と、取得が停止している状態を区別できるようにする。
- agentの生存情報だけでは機器からの取得継続を保証できないため、取得状態も扱う。

keep-aliveへの取得状態追加はcentral–agent通信規格への追記事項。対象ごとの状態粒度、期限、具体的なフィールドは未確定。

## 7. central–agent 通信規格への追記事項

1. central 起動後、全agentへ最新情報の取得を要求する。
2. 取得できた情報から提供し、未取得の対象を管理・明示する。
3. agent のkeep-aliveに取得状態を含め、centralへ伝える。

本書は追記すべき内容を整理するものであり、別のcentral–agent規格ファイルを更新したものではない。

## 8. 未決定の詳細

- 値の変化の判定方法（厳密比較、しきい値等）。
- 取得状態の種類と粒度、keep-aliveの周期・欠落判定期限。
- 通信断と取得停止の表現、復旧時の状態通知方法。
- 取得時刻、単位、型、順序情報の配置と必須性。
- 接続時の最新値一式と後続更新の順序管理。
- 配信が遅れた場合の最新値への集約方法。
- 起動識別子の形式、具体的な通信方式、メッセージ構造。

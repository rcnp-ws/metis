# Metis 警報配送：開発者向け整理

2026-09-28。自然言語による設計メモ。ここでの「合意」は会話で明示された方針を指す。具体的な API、フィールド名、保存方式、時間間隔は未確定。既存コードの挙動を記述する文書ではない。

## 用語と範囲

- 通信単位は**メッセージ**であり、**ヘッダー**と**ペイロード**を含む。
- 警報は欠落を許容しない重要なメッセージとして扱う。定期テレメトリーとは配送方針を区別する。
- 経由したサービスの一覧をメッセージに逐次追加しない。各段階の通信と処理結果を、共通の識別子で関連付けて記録する。
- `trace-id` は、システム上の発報からユーザーの acknowledge までの一連の流れを識別する。同じ警報の未確認中の再通知は同じ `trace-id` に属する。
- `message-id` は個々のメッセージを区別する。操作と警報には `trace-id` と `message-id` の両方を設ける方針。欠落を許容する定期テレメトリーにはいずれも必須としない。
- **acknowledge（確認）**はユーザーが警報を確認したこと。**異常の解消**ではない。acknowledge 後も異常監視は続く。

## 警報の流れ

1. agent 等が異常を検出し、警報を発する。一連の通知に `trace-id` を割り当てる。警報の発生と central での受付を記録する。
2. central が UI やメールなどの通知先へ配送し、通知先ごとに結果を記録する。「配送処理の受付」「送信成功」「UI に表示」「ユーザーが確認」は異なる事実として記録上区別する。
3. ユーザーの acknowledge がない間は、必要に応じて同じ `trace-id` で再通知する。発報元からの最初の通知と、後続の再通知は識別できるようにする。
4. ユーザーが acknowledge したら、その `trace-id` に属する**確認待ちの流れ**は完了する。異常状態そのものは引き続き監視する。
5. 確認後も状態が改善しなければ、新しい `trace-id` で再度発報できる。異常が解消する前に複数の `trace-id` が生まれ得る。

## ヘッダーとペイロードの検討中の情報

会話では、ヘッダーに `trace-id`、`message-id`、メッセージ発信時刻、配送試行回数を置き、ペイロードに警報の内容と、状態遷移後または acknowledge 後の最初の発報時刻を置く案が出た。**配置と必須性は未決定**である。

次の区別を維持しないと、回数と時刻が誤読される。

| 事象 | 意味 | 識別・記録上の注意 |
|---|---|---|
| 配送失敗後の再送 | 同一通知をもう一度配送する | 通知回数ではなく配送試行回数が増える。`message-id` を維持するかは未決定 |
| 未確認中の再通知 | ユーザー確認を促す新たな通知 | 同じ `trace-id` に属し、新たな発信時刻を持つ。発報・再通知回数が増える |
| 確認後の再発報 | 継続中の異常を改めて通知する | 新しい `trace-id` を割り当てる |

「最初の発報時刻」には、(a) 異常が始まった時刻、(b) 現在の `trace-id` で最初に発報した時刻、(c) acknowledge 後の最初の再発報時刻、という異なる意味があり得る。名前と意味を混同しない。後続の `trace-id` をまたいで同一異常の継続期間を追うには、異常対象と条件を関連付ける記録が別途必要になる。

## 配送確認と監査

警報に ID が付いていることだけでは確実な配送にならない。通信断、central の再起動、UI の切断、メール事業者への受け渡し、確認前のユーザー離席に対して、各段階の記録と再試行の責任を決める必要がある。UI の表示と人による acknowledge は区別する。メールサーバーへの受け渡しも acknowledge と同一視しない。

複数の通知先がある場合、どの通知先へいつ配送を試み、どこまで確認できたかを通知先単位で保持する。誰の acknowledge で流れが完了するかは未決定である。agent で発生した警報を central が受理する前に失わないための保存・再送の責任も未決定である。

## 未決定事項

1. `message-id` の単位：論理的な通知を識別し再送でも維持するか、送信試行ごとに変えるか。
2. 配送試行回数、未確認による再通知回数をどこに置き、何を初回の「0」または「1」と数えるか。
3. 未確認時の再通知間隔、上限、エスカレーション、acknowledge の期限。
4. 確認後に異常が継続した場合の再発報条件と間隔。同じ異常に由来する複数 trace の関連付け方。
5. 誰の acknowledge を有効とするか、複数ユーザーへの配送時の完了条件。
6. agent と central の永続化、再起動後の復旧、通知先ごとの到達段階の記録方法。
7. テレメトリーの鮮度・順序の扱い。追跡 ID を付けないことは古い値の識別を不要にしない。

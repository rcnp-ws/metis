# Metis 警報配送：開発者向け整理（第２版）

2026-09-28。これまでの議論で決定した設計方針。実装済みの仕様を記述するものではない。未決定事項は末尾に明示する。

## メッセージと識別子

- 通信単位は**メッセージ**であり、**ヘッダー**と**ペイロード**を含む。経路履歴をメッセージに追加せず、各地点で処理を記録する。
- 警報と操作には `trace-id` と `message-id` が必要。欠落を許容する大量の定期テレメトリーには、いずれも必須としない。全タイプに共通する必須項目とタイプ固有の必須項目は分けて定義する。
- 警報の `trace-id` は agent の一件の発報からユーザー確認までの流れを識別する。同じ警報を agent が改めて送る場合も維持する。確認後に異常条件が満たされていれば、別の `trace-id` で**新しい警報**を発報する。新旧の警報が同じ物理的な事象かどうかは、別の記録との照合によって判断する。
- `message-id` は個々のメッセージを識別する。agent→central の配送に失敗した場合は同じメッセージを再送せず、新しい `message-id` を持つメッセージを作る。再送前の失敗も agent の DB に逐次記録する。

## 警報メッセージの情報

| 項目 | 定義・決定済みの配置 |
|---|---|
| `trace-id` | 警報の一連の流れを識別する。警報メッセージに必須。**ヘッダー／ペイロードの配置は未決定**。 |
| `message-id` | 個々の警報メッセージを識別する。警報メッセージに必須。**配置は未決定**。 |
| 送信時刻 | agent がそのメッセージの送信を開始する直前に設定し、**ヘッダー**に置く。central の受信時刻や DB 保存時刻を意味しない。 |
| 異常検知時刻（最初の発報時刻） | 現在の `trace-id` に対応する最初の異常検知時刻。**ペイロード**に置き、同じ警報を改めて送る際も維持する。メッセージ作成時刻ではない。 |
| 通知トライ回数 | agent による初回の発報は **0**、同じ警報を agent が改めて発するたびに理由を問わず **1** 増やす。central から UI・メールへの通知には適用しない。**配置は未決定**。 |
| 警報内容 | 異常の対象や内容など警報固有の情報をペイロードで表す。具体的な必須項目と形式は未決定。 |

`trace-id` は共通必須項目にせず、警報・操作など必要なタイプに必須とする。通知トライ回数も警報固有であり、テレメトリーには要求しない。これらの**配置は決定していない**。「警報固有だから必ずペイロード」という扱いにはしない。

## 保存、取り込み、確認

1. agent は異常を検知し、新しい `trace-id` と異常検知時刻を記録する。送信に先立って警報を永続記憶媒体に保存する。通信断の間も、agent が活動でき保存可能な限り保持する。
2. agent は central への送信開始直前にヘッダーの送信時刻を設定する。配送失敗を DB に記録し、改めて送る場合は同じ `trace-id`、新しい `message-id`、増加した通知トライ回数を使う。
3. central は受け取るたびに agent ID と `trace-id` の組で既存記録と確認済み状態を照合する。警報を二重登録せず、確認済みの記録を未確認へ戻さない。確認済みなら agent にその状態を伝える。central の DB への保存を確定してから保存確認を返す。
4. agent は保存確認を受け取った警報の**未同期用記録**を削除する。確認が届かなければ保持する。接続復旧時には central が agent に残る警報を照会して取り込む。応答の紛失によって同じ警報が届いても、手順 3 により二重登録しない。
5. agent は保存確認後も、ユーザーの確認を待つ `trace-id` とその状態を保持する。central と agent の間で確認待ち状態が一時的に二重になることを許容する。警報の未同期用記録と確認待ち状態は削除条件が異なる。
6. ログイン可能な任意のユーザー一人が対象の確認 API を操作した時点で、central は確認者、確認時刻、対象 `trace-id` を DB に確定記録し、agent に通知する。agent は対象の確認待ち状態を終了する。通知が失われた場合は復旧後に照合し、同じ警報を agent が送ってきた際にも central が確認済み状態を返す。

ユーザーには異常を改善してから確認する責任がある。システム上の確認は**その警報の運用上の完了**であり、測定値の正常化の証明ではない。agent は監視を続け、確認後の評価でも異常条件が満たされれば新しい警報を発する。正常値への遷移は新規発報の条件にしない。

central の**DB 保存確認**は agent の未同期用記録の削除条件、**ユーザー確認の通知**は agent の確認待ち状態の終了条件である。この二つを区別する。

## UI と通知

central は警報の状態を保持し、UI に提供する。UI への状態提供と、メールなどへの能動的な通知、ユーザーによる確認は別の事実である。central で警報を保存したことだけをユーザーの確認とはみなさない。central が取り込み後に行う UI・メールへの通知は、agent の通知トライ回数に含めない。

agent は central からユーザー確認が届かなければ、一定期間後に同じ `trace-id` の警報を新たなメッセージで送ることができる。その間に central で確認済みになっていた場合は、central が受信時に確認済み状態を照合し agent に知らせる。送信間隔の値と、central による能動的な再通知の有無は未決定。

## 残る検討事項

- **フィールド配置**：`trace-id`、`message-id`、通知トライ回数のヘッダー／ペイロード上の位置、および全タイプ共通ヘッダーの必須項目。送信時刻と異常検知時刻の位置は決定済み。
- **通知設定**：agent が未確認時に改めて発報するまでの時間・上限、central からの能動的な再通知を許すかどうかと通知先・間隔。接続復旧時に取り込んだ過去の警報を通知対象とするかどうか。
- **確認状態の同期**：agent が確認待ち状態を保存する具体的な形式、central の確認通知に対する受領応答、再起動・通信断後の照合手順。
- **運用値**：記録保持期間、容量不足の事前警告と保存不能時の報告、時刻の精度と agent・central 間の時計のずれ、評価周期と測定値の揺らぎへの対応。

## 更新履歴（議論の要点）

- 初版：発報からユーザー確認までを `trace-id` で追い、配送失敗と未確認中の再通知を区別した。
- 第２版初期：agent の先行永続化、central の DB 保存後の確認、agent の未同期用記録の削除、確認 API と agent への通知を定めた。確認後の異常は新しい警報とした。
- 識別と時刻：配送失敗後は新しい `message-id` を発行する。異常検知時刻はペイロードに、送信開始直前の時刻はヘッダーに置く。agent の初回通知トライ回数は 0 とした。
- 確認状態：central は agent から警報を受け取るたびに確認済みか照合する。agent は保存確認後も、ユーザー確認が伝わるまで `trace-id` と確認待ち状態を保持する。
- 本更新：共通項目とタイプ固有項目を分け、決定済みの配置と未決定の配置を明示した。central の UI への状態提供と任意の能動的通知を分けた。
